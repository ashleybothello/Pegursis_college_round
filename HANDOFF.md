# Verity Finance ZK handoff

This directory contains the first genuine Verity Finance proof. It proves the
credit-score computation in `circuits/credit_score.circom` with Circom and a
Groth16 proof generated by snarkjs.

## Fixed model v1

```text
score = 300
      + 3 * paymentHistory
      + 2 * incomeStability
      + 1 * debtHeadroom
```

The three features are private integers in `[0, 100]`. `inputSalt` is also
private. Public inputs are:

```text
[claimedScore, modelId, taskId, inputCommitment]
```

`modelId` is constrained inside the circuit to equal `1`. The Poseidon
`inputCommitment` commits to, in order:

```text
[paymentHistory, incomeStability, debtHeadroom, inputSalt, taskId, modelId]
```

For the checked example:

```text
paymentHistory   = 82
incomeStability  = 74
debtHeadroom     = 61
claimedScore     = 755
modelId          = 1
taskId           = 42
```

The resulting `build/public.json` is:

```json
[
  "755",
  "1",
  "42",
  "6183469050151229526697960180824806002676091641771981598659326556983326480576"
]
```

The circuit recomputes and constrains this commitment; the resulting value
appears in `build/public.json`. It must not be replaced by a hash calculated
with a different hash function.

`model-config.json` is the backend/frontend copy of the approved v1 model
metadata. Keep its `modelId`, weights, public-signal order, and commitment
order synchronized with the circuit.

## Artifacts for the other engineers

After the commands in the root README section below, share these files:

- `build/credit_score.r1cs` — constraint system.
- `build/credit_score_js/credit_score.wasm` — witness calculator.
- `build/witness.wtns` — example witness satisfying the constraint system.
- `build/credit_score_final.zkey` — proving key.
- `build/verification_key.json` — verification key for off-chain verification.
- `contracts/VerityCreditScoreVerifier.sol` — generated Solidity verifier.
- `build/proof.json` — example Groth16 proof.
- `build/public.json` — matching public signals.
- `model-config.json` — shared v1 formula and signal-order metadata.
- `lib/credit-score-prover.js` — reusable backend proof-generation helper.

The proving key and example proof are demo artifacts. For a real deployment,
the trusted setup must use a properly documented multi-party ceremony and the
approved final zkey must be pinned by the application.

## Backend proof generation

The backend can generate a proof with:

```js
const {
  generateCreditScoreProof,
  verifyCreditScoreProof,
} = require("./lib/credit-score-prover");

const result = await generateCreditScoreProof({
  paymentHistory: "82",
  incomeStability: "74",
  debtHeadroom: "61",
  inputSalt: "987654321", // random per task in production
  taskId: "42",
  claimedScore: "755"
});

const valid = await verifyCreditScoreProof(result);
// result.input.inputCommitment and result.publicSignals[3] are the same.
```

The example input must contain the Poseidon commitment for the six values
listed above. Run `npm run prepare-input` to calculate it automatically. For a
production API, calculate the commitment from the approved private inputs and
return the resulting public signals and proof together; do not accept a
client-supplied commitment as authoritative.

## Smart-contract integration

The generated verifier exposes:

The generated Solidity file defines the contract `Groth16Verifier` (the file
name is `VerityCreditScoreVerifier.sol`). Person 3 can deploy that contract
directly or wrap it from `VerityManager`.

```solidity
function verifyProof(
    uint[2] calldata a,
    uint[2][2] calldata b,
    uint[2] calldata c,
    uint[4] calldata input
) public view returns (bool r);
```

The most reliable way to create the exact Solidity call arguments is:

```powershell
npm run calldata
```

That command prints the ABI-ready argument tuple. It uses the public signal
order above. Person 3 should call the verifier first, and only record a task
as verified when it returns `true` for the proof and all four public inputs.

For direct JavaScript contract calls, the Groth16 `b` coordinates need the
snarkjs-to-Solidity order shown below:

```js
const a = [proof.pi_a[0], proof.pi_a[1]];
const b = [
  [proof.pi_b[0][1], proof.pi_b[0][0]],
  [proof.pi_b[1][1], proof.pi_b[1][0]],
];
const c = [proof.pi_c[0], proof.pi_c[1]];
const input = publicSignals; // [claimedScore, modelId, taskId, inputCommitment]
await verifier.verifyProof(a, b, c, input);
```

The manager contract should store at least `taskId`, `modelId`,
`inputCommitment`, `claimedScore`, verifier result, and transaction block/time.
It should reject a proof if `input[1]` is not the approved model ID or if the
task's stored public values do not match the submitted values.

## Tamper demonstration

`npm run tamper` changes only `claimedScore` from the honest public signal to
`756` while reusing the honest proof. It must print:

```text
Honest proof verification: true
Tampered proof verification: false
```

If a provider instead tries to generate a new witness with `claimedScore: 756`,
witness generation fails because `computedScore === claimedScore` is a circuit
constraint. This is the important distinction between proving the computation
and merely storing a result or its hash.
